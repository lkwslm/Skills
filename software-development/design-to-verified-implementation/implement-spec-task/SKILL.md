# 按规格单步实施

## 前置检查

确认任务状态为 `approved`，依赖已接受，设计基线和 spec hash 与批准记录一致，允许/禁止修改范围明确。任一条件不满足即 `blocked`，不得开始编码。

若任务来自 Spec Kit、OpenSpec、Kiro Specs 或同类工具，保留并更新工具原生任务 ID 和状态，优先使用其任务执行入口。不得把原生 tasks 复制成另一份独立任务清单。

## 实施流程

1. 只读取当前 `TASK-*`、其 `SPEC-*`、直接来源需求、相关接口和必要代码；不要把其他待办顺手带入。
2. 复述本任务的可观察完成条件、允许变更范围和验证命令。
3. 先运行现有基线测试；修 bug 时先建立可复现失败，新增行为时先写或补充会失败的验收/契约测试。
4. 做满足该任务的最小变更。遵循仓库风格，不做无关重构或“未来扩展”。
5. 运行任务测试、受影响回归、接口契约检查，以及 spec 指定的 E2E/NFR 检查。
6. 生成 [evidence-template.md](assets/evidence-template.md)；记录真实命令、退出码、结果、环境、diff 范围和未验证项。
7. 把状态改为 `verifying`，交给不同 agent 调用 `$audit-spec-conformance`。实现者无权标记 `accepted`。

## 不可越权规则

- 不得修改 spec、验收标准、设计基线或测试预言来迁就实现。
- 发现矛盾、缺失接口或不可实现条件时，返回 `blocked` 并指出对应 ID；不得自行作产品决策。
- 任何任务外行为变化必须创建 `CR-*` 并回到审批门禁。
- 测试跳过、 flaky 重试后偶然成功、无命令输出或仅有自述均不算通过。
- 若审计失败，只修复报告中有证据的差异；若根因是 spec 错误，退回 Spec 作者。
