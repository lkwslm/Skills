# 设计文档建账

## 输入与边界

读取用户指定的设计文档、仓库规则和已有 `.specflow/`。只做事实提取、规范化和冲突发现；不写实现方案，不擅自裁决矛盾。

## 工作流

1. 枚举来源文件，记录路径、内容 hash、标题结构和版本。不得只保存摘要。
2. 按标题与语义边界分块读取；为每块保留可复查的 `文件#标题/行号` 定位。
3. 先建立术语、实体、状态机、权限和数据字典，再抽取局部需求。
4. 将陈述原子化为 `REQ-*`、`NFR-*`、`INV-*`、`DEC-*`、非目标和示例。一个 ID 只表达一个可判定意思。
5. 对每项记录规范化描述、强度、来源引用、适用范围、依赖、验收线索和状态。
6. 专门扫描“必须、不得、仅当、至少、至多、默认、超时、容量、兼容、回滚”等限定词及数字/单位，确认没有在摘要中降级。
7. 比较跨章节定义，建立 `OPEN-*`：列出冲突来源、候选解释、影响范围、风险和待决策人。
8. 运行覆盖复查：把每个原文段落到需求/术语/问题的映射写入 `source-coverage.csv`；每个规范性段落至少映射一个 ID，或明确标为背景/示例/非规范内容。
9. 使用 [baseline-template.md](assets/baseline-template.md) 生成或更新工件；保留既有稳定 ID。
10. 单独初始化或更新交付矩阵 `traceability.csv`，严格使用 `requirement_id,source_refs,spec_id,task_ids,test_ids,implementation_refs,evidence_refs,status` 列。建账阶段允许下游列为空。不得把来源覆盖 schema 写入该文件。

## 长文档策略

- 先索引后细读；按领域批次处理，批次结束即写入持久工件。
- 摘要仅导航，Spec 作者必须能沿来源引用回到原文。
- 每批同时检查全局不变量、术语和接口，避免分块后丢失跨模块约束。
- 不确定是规范还是示例时创建开放问题，不要自行提升或降级其效力。

## 门禁

只有同时满足以下条件才标记基线 `resolved`：

- 所有规范性内容均被覆盖或显式排除；
- 每项有稳定 ID 和精确来源；
- 核心术语不存在重复定义；
- 高影响 `OPEN-*` 已关闭；
- 来源 hash 与当前文件一致。

输出变更摘要、未决问题和受影响的旧 spec。不得声称已消除所有偏差，只能报告覆盖证据与剩余风险。
