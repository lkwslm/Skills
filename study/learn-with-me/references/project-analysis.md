# 项目拆解协议

## 统一起点

把项目要解决的“问题与目标”作为根节点；业务目标、技术问题、开发者问题和用户任务都是具体分支。按下列链条向实现推导：

```text
问题与目标
→ 场景与约束
→ 所需能力
→ 领域规则
→ 数据与状态
→ 交互与流程
→ 设计决策
→ 模块与接口
→ 代码与测试
```

仓库目录是实现证据，不是默认学习顺序。

## 够用的项目全景

第一课前只调查到足以解释前几个单元顺序：

- 项目解决的问题、目标用户和关键场景；
- 入口、主要运行路径、核心模块和数据边界；
- 测试结构、显式设计文档及当前版本；
- 初始目标链，以及 `roadmap.md` 中的重要设计切片覆盖地图。

其余代码随学习单元按需深入。不要先生成全仓报告，也不要按文件顺序阅读。

## 证据分层

在课程中显式标记：

- **事实**：代码、测试、项目文档、issue 或提交历史直接支持；给出文件、符号、版本或链接。
- **作者说明**：维护者明确表达的动机；给出原始来源。
- **推断**：从多个事实推导出的设计解释；写出推导链和置信度。
- **假设**：证据尚不足、等待验证的解释；列出可以证伪或升级它的证据。

发现新证据时允许调整层级。不得把合理故事写成作者动机。

## 选择点与替代设计

每个单元都检查真实选择点。存在时选择 2–3 个在相同约束下可行的方案，比较：

| 维度 | 要回答的问题 |
|---|---|
| 解决的问题 | 方案改善了哪个目标或约束？ |
| 新复杂度 | 引入哪些认知、运行或维护成本？ |
| 适用条件 | 什么条件下优于原设计？ |
| 实现后果 | 模块边界、数据流、接口和关键代码怎样变化？ |
| 故障模式 | 会增加哪些失败路径或运维风险？ |

替代设计必须推导到代码层后果。没有真实选择点时明确写“不适用”及理由。

## 覆盖完成标准

重要目标与设计切片必须达到“已覆盖”或留下学习者认可的排除理由。文件阅读数量不构成覆盖证据。
