# 单个开源项目调研

输出一份以决策为导向、由一手资料支撑的中文 Markdown 调研。默认进行工作流级静态调研，不实际部署项目。

## 1. 建立调研基准

确认唯一的官方项目仓库，并获得一份足以判断适配性的需求画像：

- 想解决的问题；
- 必须具备的能力及硬约束；
- 可以接受的缺口；
- 部署和资源环境；
- 安全、隐私与许可证边界；
- 社区成熟度要求。

可从环境或官方资料查到的事实直接查证。缺少会改变结论的需求决策时，一次只问用户一个问题，并给出推荐答案。需求画像足以区分硬约束与偏好后，才开始适配判断。

若项目名称对应多个仓库、历史仓已迁移或官方仓不明确，先消除项目身份歧义。

## 2. 建立证据集

优先使用以下一手来源：

1. 官方仓库与 README；
2. 官方文档；
3. LICENSE、部署清单、Release 和维护记录；
4. 官方 Issue，仅用于确认限制、争议或未完成能力；
5. 核心源码，仅在官方说明缺失、含糊或相互矛盾时补证。

动态事实注明核验日期。把官方声明、源码事实和调研者判断分开表达。官方没有说明且无法验证的能力标记为“未确认”，不从相邻功能推定支持。

## 3. 还原工作方式

先解释项目面对的具体问题和设计选择，再还原：

```text
输入 → 关键处理阶段 → 状态或产物 → 输出
```

处理阶段达到三个时，使用 Mermaid 工作流图。用阶段说明解释每一步做什么、产生什么、由什么证据支持。产品截图和 Logo 不进入报告。

默认不安装或运行项目。部署清单仅用于识别进程、服务、存储、中间件、可选组件和它们之间的关系。

## 4. 对照需求

逐项建立需求矩阵，不用项目亮点替代需求：

- 状态只使用“满足、部分满足、不满足、未确认”；
- 每一项能力都给出项目证据；
- 硬约束不满足时，必须进入最终否决风险；
- 需要插件、商业版、SaaS、外部服务或自研适配才能实现时，状态不能写成无条件“满足”。

## 5. 形成结论

适配结论只使用以下一级：

- **直接匹配**：核心能力可直接满足，仅需常规接入；
- **条件匹配**：核心思路合适，但存在必须补齐的适配、部署或治理缺口；
- **仅供借鉴**：现成项目不适用，但数据模型、架构或交互值得复用；
- **不匹配**：关键目标或硬约束冲突。

结论必须由需求矩阵推导，并分别交代已满足能力、能力缺口、需要自研的部分、否决风险和下一步验证项。评分不能代替这一级结论。

## 6. 生成报告

收集证据并完成判断后，完整读取 [references/report-template.md](references/report-template.md)，严格按照它的章节顺序生成报告并输出到用户指定的目录，如果没有指定，默认在项目根目录下生成文档。

写作遵循以下约束：

- 正文使用模板规定的八个主章节；
- 每章包含多个有意义的段落、子标题、列表或表格，一个段落只表达一个观点；
- 用结构拆分信息，不把整章压成一段，也不为满足形式制造空话；
- 项目快照保持一行，只含仓库、核验日期、Stars、许可证、最近发布或维护状态；
- 事实用语义化 Markdown 脚注引用一手来源；
- 推断显式写成“调研判断”，未确认事项保留为待验证项；
- 部署章节只列组件、关系、持久化和可选项，让读者判断难易，不给轻、中、重评分，也不虚构资源数字。

## 完成标准

仅当以下条件全部满足时完成：

- 项目身份和需求画像无影响结论的歧义；
- 八个主章节均有实质内容且没有单段堆叠；
- 工作流的输入、处理、状态或产物、输出全部可追踪；
- 需求画像中的每个需求均出现在对照表中；
- 开源核心、商业版、SaaS 和外部依赖没有混写；
- 部署构成覆盖所有主要持久化与运行组件；
- 适配结论属于四级之一，并能由需求矩阵复核；
- 所有关键事实有一手来源，所有脚注已定义且动态信息有核验日期。
